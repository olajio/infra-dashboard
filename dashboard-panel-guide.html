Why panels sit where they do

Section 3 is deliberately after the operational detail rather than buried at the bottom: a coverage gap or a stale feed means the availability figures in sections 1 and 2 are optimistic, so it reads as the confidence statement for everything above it. Alert correlation and deduplication sit in section 4 rather than with the alert-handling detail because they measure what automation removes from the analyst queue — the same question the predictive tiles ask.

Terminology — Affected CI vs Impacted CI

Aligned to the client’s definitions, September 2026. An earlier version of this dashboard had the two terms the other way round; every panel title, column label and note has been realigned.

TermDefinitionOn the dashboard
Affected CIThe configuration item that is affected by the incident — the server, switch, database or service the incident was raised against.ci.name on the ServiceNow incident record. This is what every CI panel shows today.
Impacted CIA configuration item that could be affected as a consequence of the affected CI failing — the downstream, dependent side of a CMDB relationship.Not available yet.

Panels renamed: Impacted CIs — Active P1 / P2 Incidents → Affected CIs — Active P1 / P2 Incidents; Servers Down — Impacted CIs → Servers Down — Affected CIs. Impacted Domain keeps its name (a domain is not a CI) but its CI column is now Affected CIs.

Why Impacted CIs are not on the dashboard

Deriving them needs the CMDB relationship graph in cmdb-ci-relations-000002 (33.9M edges: parent, child, type.name, and an impacted_ci field naming which side is downstream). ES|QL cannot traverse a graph that size at query time, and ci.parents.* / ci.top_level_parents.* exist in the incident mapping but are populated on 0 documents, so the incident record carries no downstream rollup of its own. Closing this needs an ENRICH policy or a denormalising transform on the Elasticsearch side — an infrastructure change, not a dashboard one. business_service.name is populated on 2.8% of incidents and is the nearest available proxy; it is shown on the Affected CIs worklist.

Reconciling the incident counts

The client found three different P2 figures on one screen. Three panels, three numbers, two separate causes — both now fixed.

Fixes. To verify against the cluster:

FROM servicenow-open-incidents-snapshots-*
| WHERE priority == 2
| STATS all_p2 = COUNT_DISTINCT(number),
        with_ci = COUNT_DISTINCT(CASE(ci.name IS NOT NULL, number, null))
| EVAL no_ci = all_p2 - with_ci
FROM servicenow-open-incidents-snapshots-*
| WHERE priority == 2 AND ci.name IS NOT NULL
| STATS rows = COUNT(*) BY number, ci.name, ci.class_name, ci.environment,
                           assignment_group.name, business_service.name, short_description
| STATS variants = COUNT(*) BY number
| WHERE variants > 1

The first should return no_ci = 4; the second should return the one incident that was splitting.

Scope — what the availability number covers

metrics-* is not a server-only index pattern: it spans 578 data streams and ~830M documents across eleven tiers. But host.name is only a valid availability unit for agent-based collection (system.*, windows.*), where it names the monitored machine. For remotely-collected tiers the agent writes its own hostname, so host.name is the collector — vsphere.virtualmachine carries 150,838 documents under a single host.name, every kubernetes.* stream shows 1, and gcp.gke shows 1 for 197M documents.

An unscoped COUNT_DISTINCT(host.name) therefore mixes real servers with APM service hosts, containers and collector hostnames. Every availability panel is now scoped with | WHERE STARTS_WITH(data_stream.dataset, "system."), so the denominator is the real server estate of ~2,893 hosts.

How to say it in the room: availability is measured on the OS-monitored server estate; P1/P2 covers every infrastructure domain; collection health for the other tiers is panel 2.9.

The RAG rule, in full

Evaluated top–down inside the panel’s ES|QL, so RED always wins over AMBER.

RED

Any active P1 in any domain, or CI availability below 99%.

AMBER

Any active P2 in any domain, or CI availability below 99.9%.

GREEN

No P1, no P2, CI availability 99.9% or better.

Re-tuning is a one-line edit: open the panel, Edit ES|QL, change 99.0 or 99.9 in the EVAL infra_health block. The boundaries are the two-nines / three-nines availability tiers, deliberately the same as the RAG colouring on the availability tiles so the two never disagree about what green means.

2.1

Overall Infrastructure Health

data tablemetrics-* + servicenow snapshots

Is infrastructure healthy right now — one answer, one colour.

A single ES|QL statement reads both indices at once, using METADATA _index to tell the two document sources apart. That is what lets availability and incident load be scored together rather than in two panels the reader has to combine mentally.

Changed September 2026 — CI availability, not server availability. The denominator is now every CI with ci.is_monitored == true and ci.operational_status == "Operational", counted on ci.name, rather than distinct host.name on system.* datasets. That is a wider population — it includes CIs monitored through tiers where host.name is the collector rather than the device (vSphere, Oracle, MQ, GCP), which the server-based figure could never see. Expect this number to differ from the Server Availability % tile beside it: they measure different estates and both are correct.

| EVAL infra_health = CASE(
      p1 > 0 OR availability_pct < 99.0,  "RED",
      p2 > 0 OR availability_pct < 99.9,  "AMBER",
      "GREEN")

2.2

Server Availability %

metricmetrics-* scoped to system.*

What percentage of the server estate is alive?

Denominator: distinct host.name shipping system.* telemetry anywhere in the dashboard time window — about 2,893 servers. Numerator: the same, restricted to hosts with a document in the last 15 minutes. Shown to two decimals, matching the 99.5% example in the feedback.

Renamed from Infrastructure Availability %. The KPI is unchanged; the title now states its scope, because the figure is a server-estate number and the old name implied the whole estate.

Worth saying out loud when presenting: “up” means still shipping metricbeat data. A box that is powered on but whose agent has died counts as down — deliberately, because that is a real monitoring outage.

RAG colouring (September 2026). Both availability tiles — this one and Servers Availability % in the operational row — now colour the number against the standard availability tiers: 🟢 green at 99.9% or better (three nines), 🟠 amber from 99.0% to 99.9% (two nines), 🔴 red below 99.0%.

Read this before adopting those thresholds

At roughly 3,139 monitored servers, three nines is 3 hosts. A routine patch window that reboots a dozen machines will show amber, and a larger maintenance wave will show red — correctly by this definition, but noisily if the team reads the tile as an alarm rather than a status. If that is too tight for how this estate is actually run, the usual alternative is green at 99.5% and amber at 99%. It is a two-number edit to the colorStops in each tile’s palette.

2.7

Application Health — APM

data tableapm.service_transaction.1mAPM drill-down

Which business applications are failing, in which portfolio and environment?

One row per business application × portfolio × environment, sorted worst-first: Health (🔴 RED ≥ 5% errors, 🟠 AMBER ≥ 1%, 🟢 GREEN below), Business application, Portfolio, Env, Error rate %, Avg latency (ms), Failed txns and Transactions.

How the maths works. event.success_count and transaction.duration.summary are aggregate_metric_double fields — each document stores {sum, value_count} rather than a single number. In ES|QL COUNT(field) returns the summed value_count and SUM(field) the summed sum:

error rate  = (COUNT(event.success_count) − SUM(event.success_count)) / COUNT(event.success_count)
avg latency = SUM(transaction.duration.summary) / COUNT(transaction.duration.summary)

That is exactly how Elastic’s own APM UI derives failure rate, so this dashboard and the APM app agree.

Sanity check after import: if Transactions equals the raw document count on every row, this build is not unwrapping value_count and the rates are wrong. txns should come back well above docs here:

FROM metrics-apm*
| WHERE data_stream.dataset == "apm.service_transaction.1m"
| STATS docs = COUNT(*), txns = COUNT(event.success_count), ok = SUM(event.success_count)

Drill-down into APM. Click a value in the APM service column and that service’s APM overview opens in a new tab:

/app/apm/services/<service.name>/overview?rangeFrom=now-24h&rangeTo=now&environment=ENVIRONMENT_ALL

Two constraints shape this, both worth knowing before anyone asks. The drilldown has to be pinned to one column. A Lens ES|QL table fires the click action on every column it treats as a dimension, so the drilldown was originally offered on cells whose value was never meant to reach the URL. Every column except service.name is now marked as a metric (inMetricDimension), which is what decides whether a cell is clickable, so the action appears on the APM service column alone.

Correction

An earlier version of this guide said Kibana only offers a drilldown on columns backed by a real index field, and that EVAL/STATS-computed columns were inert on click. That is not true of ES|QL tables — the client found the ServiceNow link offered on every column of the CI worklist. Wrapping a column in TO_STRING() does not make it unclickable; marking it as a metric does.

The link must key on service.name, not the business application name. APM addresses services by service.name (document management facility prod); the ServiceNow name (Document Management Facility) resolves to a service APM does not have. The table therefore shows the business application as the label and carries service.name as the clickable column beside it — which also means the table is now one row per APM service, with its business application alongside.

On ES|QL tables: the URL field formatter — the usual way to turn a cell into a hyperlink — does not render as a link in ES|QL-backed Lens tables, only data-view-backed ones. The URL drilldown is the supported route here, which is why the value opens on click rather than looking like a blue link.

Application naming. APM documents carry the CMDB Business Application enrichment — ci.name (Document Management Facility), ci.number (APM0003276), ci.customer_specific.pm_portfolio (Policy Admin (Commercial and Specialty)) and ci.support_group.l2.name. Panels key on COALESCE(ci.name, service.name) so unenriched services still appear under their raw APM service name.

2.9

Monitored Estate — Coverage by Tier

data tablemetrics-*

What is actually being monitored, and is each tier still reporting?

One row per infrastructure tier, derived from data_stream.dataset: Servers (OS and Windows), Applications (APM), vSphere, Oracle, SQL, IBM MQ, GCP, Kubernetes, Prometheus targets and the monitoring stack itself. Columns show how many data streams feed the tier, its distinct host.name count, document volume, minutes since the last document, and a collection status of Flowing (≤15 min), Delayed (≤60 min) or Stalled.

Read the host column carefully: for remotely-collected tiers it is the collector count, not a device count. This is a collection-health view, not per-device availability — that needs each tier’s own entity identifier rather than host.name.

2.11

Affected CIs — Active P1 / P2 Incidents

data tableservicenow-open-incidents-snapshots-*CMDB drill-downrenamed

Which CIs are the open P1s and P2s actually sitting on?

The incident-side worklist: every open P1/P2 with the CI it landed on — Sev, Incident, Affected CI, CI class, Business service, Env, Assigned to, Short description, Last seen.

Drill-down — direct CMDB record link. Clicking the CMDB record column opens that CI in ServiceNow at nav_to.do?uri=cmdb_ci.do%3Fsys_id%3D<ci.sys_id>. sys_id is the CI’s primary key, so ServiceNow resolves the record and renders it on its own class form — a Windows server opens as a Windows server. That is what the team asked for when they said the old link went to “the base link for the CI”, and it needs no class parameter at all.

Why there is a separate column for it. A Kibana URL drilldown receives exactly one value: the cell that was clicked. It cannot read the rest of the row, so whatever the URL needs must be the clicked cell — which means a column has to carry it. Affected CI stays clean and readable and is no longer clickable; cmdb_record is the only clickable column and is width-capped at the end of the row.

The link column — what was traded away

The class-scoped list URL the team originally sent (cmdb_ci_list.do?sysparm_query=name%3D…%5Esys_class_name%3D…) needs two values, so the clicked cell had to carry vskau1p1328^sys_class_name=cmdb_ci_win_server — accurate, but ugly in an executive table. sys_id reaches the same record with one opaque reference id, which reads like the record pointer it is.

Check on import: if the CMDB record column is blank, ci.sys_id is not populated on servicenow-open-incidents-snapshots-* and the link has nothing to key on. The fallback is the class-scoped list URL, which goes back in on request.

Fixed September 2026 — phantom “down” servers

The client reported the Servers Down tile showing 0 while the table listed a screen of dead servers — one of which (kw3lniicsd002) was demonstrably reporting CPU metrics a minute earlier.

The table used to group on seven keys: host.name plus six CMDB enrichment attributes (ci.name, ci.class_name, ci.environment, ci.geo.name, ci.support_group.l2.name, ci.short_description). Those attributes are mutable. When a CI’s enrichment changes, documents written before the change keep the old values and documents after carry the new ones — so one host becomes two groups. The group holding the superseded values has a last_seen frozen at the moment of the change, sails through WHERE last_seen < NOW() - 15 minutes, and is rendered as a dead server. The host is alive; only that combination of attribute values is.

The tell was in the data: every phantom row read 1,425–1,426 minutes down — 23 h 45 m, landing a few minutes inside a 24-hour window. That is not a fleet of servers failing independently, it is one bulk CMDB update at a single moment, just inside the window’s reach. All of them were Linux servers in the same data centre under the same support group.

The Servers Down tile was never wrong: it counts COUNT_DISTINCT(host.name) with no attribute grouping, so a host is one entity however often its metadata changed.

The fix. Group on host.name alone, then collapse the CI columns onto that row with VALUES(...) + MV_MAX(...). The table’s definition of down is now identical to the tile’s, so the two agree by construction rather than by coincidence.

The same defect exists in Coverage Gap — Monitored CIs Not Reporting, which groups on ci.name, host.name, ci.geo.name and ci.support_group.l2.name. It is not fixed here because the fix trades away a feature: the two descriptive columns would stop being index-backed and lose click-to-filter. Applications on Silent Servers had the same defect and is fixed, because its displayed columns do not change.

On “affected CI”

This shows the CI that is down plus what the CMDB says it is for. It does not show downstream CIs that depend on it — that needs the cmdb-ci-relations-* graph joined to the host list, which ES|QL cannot do at query time against a 33.9M-edge index. It needs an ENRICH policy or a denormalising transform on the Elasticsearch side.

The one open item

Impacted domain and impacted applications are CMDB-derived, not incident-derived

The only fields confirmed to exist on servicenow-open-incidents-snapshots-* today are number and priority. ci.name is not populated on those incident documents — the ci_name_exists.csv export came back empty — so incidents cannot be joined to CMDB configuration items on CI name, and no category, assignment-group or business-service field has been confirmed either.

So panels 2.6 and 2.7 answer “which domains and applications have infrastructure that has gone silent”. That is a true impact signal and it is live today — but it is not a breakdown of the P1/P2 incidents themselves. Worth stating plainly in the presentation rather than letting someone discover it in the room.

To close it, run this in Discover → ES|QL and share the column list:

FROM servicenow-open-incidents-snapshots-*
| WHERE priority <= 2
| LIMIT 5

Once a domain/category field and a business-service field are confirmed, both panels swap to incident-based ES|QL and nothing else on the dashboard changes — the RAG tile already reads P1 and P2 straight from that index.

FROM servicenow-open-incidents-snapshots-*
| WHERE priority <= 2
| STATS p1 = COUNT_DISTINCT(CASE(priority == 1, number, null)),
        p2 = COUNT_DISTINCT(CASE(priority == 2, number, null))
  BY domain = <category_or_assignment_group_field>
| SORT p1 DESC, p2 DESC

Limitations to state up front

  • MTTA is still blocked. acknowledged_at, assigned_at and assigned_by are absent from servicenow-incidents-*. It needs a ServiceNow Business Rule to write the Acknowledge state-change timestamp, plus a mapping update on the Elastic integration.
  • Noise Reduction Opportunity Score is still blocked — no stable rule identifier, no dedup outcome, no analyst-feedback flag, no alert-to-incident join key.
  • Environment scope. Availability and impact currently span every environment: prod, drt, cut, ete, dre, dev, test, sandbox, eit. If leadership wants the executive row to be prod-only, add a ci.environment control beside the existing three, or add AND ci.environment == "prod" to those panels.
  • “Up” means shipping telemetry, not responding to a probe. Intentional, but say it before someone else does.
  • No per-device availability outside the server estate. vSphere VMs, Oracle instances, MQ queue managers, GCP resources and Kubernetes objects are collected remotely, so host.name is the collector. Measuring their availability needs each tier’s own entity field; panel 2.9 is the interim collection-health signal.
  • The APM application register is now on the dashboard (panel 2.10). The CMDB-derived Impacted Applications panels are kept rather than replaced, because they answer a different question: which applications sit on servers that have gone silent.

Deploy by importing operation-dashboard.ndjson under Stack Management → Saved Objects → Import, choosing “Check for existing objects” and overwriting, so the dashboard keeps its URL and bookmarks. The file carries the metrics-* data view and the dashboard; every panel is stored by value, so there is nothing else to create.
